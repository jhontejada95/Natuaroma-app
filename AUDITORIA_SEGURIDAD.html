1. Resumen Ejecutivo

Se realizó una auditoría completa del código fuente del proyecto, revisando todos los archivos de rutas, server actions, middleware, configuración y componentes críticos. Se identificaron 17 hallazgos clasificados por severidad. El proyecto tiene una arquitectura sólida pero presenta 3 vulnerabilidades críticas que deben resolverse antes de escalar operaciones.

✅ Fortalezas Identificadas
Separación correcta de clientes Supabase (createClient / createAdminClient) — resuelve una clase entera de bugs de autenticación
RLS activo en 5 tablas con políticas correctas para datos de usuarios
HMAC implementado en webhook de MercadoPago (esperando secret en Vercel)
Server Actions protegen automáticamente contra CSRF vía Origin header check
Rutas muertas desactivadas con 410 — sin dead endpoints explotables
Service Role Key nunca expuesto al cliente, solo en server-side
Idempotencia en activación de códigos (.is('activated_at', null))
findUserByEmail() via REST API evita timeout de listUsers() en Vercel
⚠️ Issues que Requieren Atención
CRÍTICO: Admin Server Actions sin verificación de autorización — cualquier usuario autenticado podría ejecutarlas
CRÍTICO: Stock nunca se decrementa al completar un pago (overselling)
CRÍTICO: Quantity del carrito no validada — puede ser negativa (precio negativo)

2. Respuestas a las Preguntas de la Auditoría

2.1 — SQL Injection: ¿Estamos protegidos?
✅ SÍ, con matices menores

El proyecto usa exclusivamente el SDK de Supabase (@supabase/supabase-js) para todas las operaciones de base de datos. Este SDK construye queries parametrizados internamente — los valores nunca se concatenan directamente al SQL. No se encontró ningún uso de raw SQL, db.rpc() con template literals, ni query() con strings concatenados.

PatrónCódigo ActualVeredicto
SELECTs.from('products').select().eq('id', id)✅ Seguro — parametrizado
INSERTs.insert({ code, user_email, source })✅ Seguro — objeto tipado
Raw SQLNo encontrado en ninguna ruta crítica✅ OK
Validación de inputs.trim() / .toLowerCase() manual — sin Zod⚠️ Incompleto — ver M-01
URL REST API (setup/actions.ts)encodeURIComponent(email) correcto✅ Bien manejado

Nota: El proyecto no usa un ORM clásico (Prisma, Drizzle). El SDK de Supabase actúa como query builder con parametrización automática — equivalente en protección a usar un ORM.

2.2 — CORS: ¿Tenemos configuración?
⚠️ No configurado explícitamente — no es problema hoy, sí al escalar

Next.js App Router no agrega headers CORS a las API Routes por defecto. El único endpoint expuesto es el webhook de MercadoPago (/api/webhooks/mercadopago), que es server-to-server y no necesita CORS. Las Server Actions están protegidas por CSRF vía Origin header check de Next.js.

EndpointEstado CORSEvaluación
/api/webhooks/mercadopagoSin CORS — server-to-server✅ No necesita CORS
Server ActionsCSRF protegido por Next.js (Origin check automático)✅ OK — pero falta autorización (C-01)
Si se agrega API pública (v2)Sin configurar — BLOQUEANTE⚠️ Configurar antes de crear endpoints

Recomendación: Agregar security headers en next.config.ts (ver A-03). Cuando se creen endpoints de API pública, configurar CORS explícitamente.

2.3 — DDoS: ¿Estamos protegidos?
⚠️ Protección parcial a nivel de infraestructura, ninguna a nivel de aplicación
CapaEstado ActualEvaluación
Red (L3/L4)Vercel Edge Network — protección básica incluida✅ OK para operación actual
HTTP / Aplicación (L7)SIN rate limiting en ninguna ruta❌ Vulnerable a flood de órdenes, brute force en login admin, spam de /registro
Bot detectionNo configurado⚠️ Sin Vercel WAF o Cloudflare activos

Solución recomendada: Implementar Upstash Redis + @upstash/ratelimit. Con el plan gratuito de Upstash es suficiente para el volumen actual. Ver issue A-01 para el código de implementación.

2.4 — Colas (Queues): ¿Usamos alguna para resiliencia?
⚠️ NO — todos los procesos son síncronos y en cadena

Actualmente todas las operaciones post-pago (emails, creación de wellness access, notificación Telegram) se ejecutan en secuencia dentro de la misma petición HTTP. Los puntos de fallo son:

  • Webhook MercadoPago: Los emails están en Promise.allSettled() ✅ pero si la DB falla no hay retry automático.
  • Registro físico: La notificación de Telegram se envía síncronamente sin timeout. Si Telegram está caído, bloquea la respuesta al usuario.
  • No hay mecanismo de reintentos para operaciones fallidas a mitad del flujo.

Para el volumen actual, Promise.allSettled + logs es aceptable. Al superar ~50 órdenes/día, considerar Inngest o Trigger.dev — ambos tienen free tier generoso y se integran nativamente con Next.js en menos de 15 minutos.

⚠️ Validación parcial — no hay schemas que garanticen la forma en toda la cadena

3. Tabla de Hallazgos por Severidad

🔴 CRÍTICO — Acción Inmediata Requerida
CRÍTICO C-01 Admin Server Actions sin verificación de autorización
📁 admin/orders/actions.ts · admin/products/actions.ts · admin/wellness/actions.ts · admin/wellness/contenido/actions.ts
Descripción e Impacto
El middleware protege las rutas del admin, pero las Server Actions son endpoints HTTP POST independientes. Los action IDs están en el bundle de JS — un usuario logueado (no admin) puede encontrarlos y llamar a updateOrderStatus(), deleteProduct(), createInvitation(), etc. directamente desde cualquier cliente HTTP.

Impacto: Broken Access Control (OWASP A01) — cualquier usuario autenticado puede eliminar productos, cambiar estado de órdenes, o crear códigos Wellness sin ser admin.
Solución Recomendada
Agregar verificación de rol al inicio de cada server action del admin:
// Al inicio de CADA admin action:
const supabase = await createClient()
const { data: { user } } = await supabase.auth.getUser()
if (!user) redirect('/admin/login')

const db = createAdminClient()
const { data: profile } = await db
  .from('profiles')
  .select('role')
  .eq('id', user.id)
  .single()
if (profile?.role !== 'admin') {
  throw new Error('Unauthorized')
}
CRÍTICO C-02 Stock de productos nunca se decrementa (overselling)
📁 checkout/actions.ts · api/webhooks/mercadopago/route.ts
Descripción e Impacto
El stock se verifica antes de crear la orden, pero nunca se actualiza en la base de datos. Race condition clásica: dos usuarios comprando el último producto simultáneamente generan dos órdenes válidas con el mismo artículo.

El campo stock en la tabla products nunca cambia con ninguna venta.

Impacto: Overselling, inconsistencia de inventario, promesas de entrega imposibles, problemas operacionales con clientes.
Solución Recomendada
Decrementar stock atómicamente en el webhook al confirmar pago:
// En webhook, al marcar 'approved':
// 1. Crear función SQL en Supabase:
CREATE OR REPLACE FUNCTION decrement_stock(
  p_product_id uuid, p_qty int
) RETURNS void AS $$
  UPDATE products
  SET stock = stock - p_qty
  WHERE id = p_product_id
    AND stock >= p_qty;
$$ LANGUAGE sql;

// 2. Llamar desde el webhook:
for (const item of orderItems) {
  await db.rpc('decrement_stock', {
    p_product_id: item.product_id,
    p_qty: item.quantity
  })
}
CRÍTICO C-03 Quantity del carrito no validada — puede ser negativa
📁 checkout/actions.ts línea 24 · checkout/page.tsx
Descripción e Impacto
La quantity viene del localStorage del cliente (Zustand). El servidor no valida que sea un número entero positivo. Si un atacante envía quantity: -100, el subtotal resulta negativo y MercadoPago podría crear una preferencia con monto cero o negativo.

El check de stock actual (p.stock < item.quantity) no detecta negativos — si quantity es -1 y stock es 5, 5 < -1 es false y la orden se crearía.

Impacto: Potencial compra gratuita o crash en flujo de pago.
Solución Recomendada
Agregar validación numérica antes de procesar cada item:
// Después del JSON.parse, validar cada item:
for (const item of cartItems) {
  const qty = parseInt(String(item.quantity), 10)
  if (!qty || qty < 1 || qty > 99) {
    redirect('/checkout?error=Cantidad inválida')
  }
  item.quantity = qty // sanitized integer
}

// También asegurar que el precio final sea > 0:
if (total <= 0) {
  redirect('/checkout?error=Total inválido')
}
🟠 ALTO — Resolver antes de Escalar
ALTO A-01 Sin rate limiting en ninguna ruta
📁 Todas las rutas: checkout, login admin, registro físico, webhook
Descripción e Impacto
No existe ningún mecanismo para limitar cuántas veces un IP puede llamar a los endpoints. Vectores de ataque:

• Brute force en /admin/login — no hay lockout
• Spam de /registro — crear miles de registros físicos falsos
• Flood de órdenes en /checkout — saturar DB y Resend
• Replay attacks al webhook sin HMAC activo

Vercel tiene protección a nivel de red (L3/L4) pero no limita a nivel de aplicación (L7).
Solución Recomendada
Implementar Upstash Redis + @upstash/ratelimit (free tier: 10k req/día):
// lib/ratelimit.ts
import { Ratelimit } from '@upstash/ratelimit'
import { Redis } from '@upstash/redis'

export const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(10, '1 m'),
})

// En cada server action crítica:
import { headers } from 'next/headers'
const ip = (await headers()).get('x-forwarded-for') ?? 'anon'
const { success } = await ratelimit.limit(ip)
if (!success) redirect('?error=Demasiados intentos. Espera 1 minuto.')
ALTO A-02 Math.random() para códigos de acceso Wellness
📁 checkout/actions.ts:99 · webhooks/mercadopago/route.ts:114 · registro/actions.ts:44 · admin/wellness/actions.ts:9
Descripción e Impacto
Math.random() no es criptográficamente seguro. Está optimizado para velocidad, no para impredecibilidad. Con 6 caracteres base36 el espacio es de ~2.8 billones de combinaciones — fuerza bruta factible en minutos con un script automatizado si no hay rate limiting.

Impacto: Un atacante podría predecir o enumerar códigos de acceso Wellness sin haber pagado.
Solución Recomendada
Reemplazar en todos los lugares con crypto.randomBytes():
// lib/utils.ts
import { randomBytes } from 'crypto'

export function generateWellnessCode(): string {
  // 8 chars de un alfabeto de 32 chars = 32^8 = ~1 billón
  const chars = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789'
  const bytes = randomBytes(8)
  const code = Array.from(bytes)
    .map(b => chars[b % chars.length])
    .join('')
    .slice(0, 8)
  return 'NAT-' + code
}

// Reemplazar Math.random() en los 4 archivos afectados
ALTO A-03 Sin headers de seguridad HTTP
📁 next.config.ts
Descripción e Impacto
El servidor no envía ningún header de seguridad. Sin Content-Security-Policy, sin X-Frame-Options, sin X-Content-Type-Options, sin Strict-Transport-Security. Esto expone la app a:

• Clickjacking — la página puede ser embebida en un iframe
• MIME sniffing — el navegador puede interpretar respuestas como scripts
• XSS — sin CSP, scripts inyectados tienen acceso total

Herramientas como securityheaders.com darían calificación F.
Solución Recomendada
Agregar en next.config.ts:
async headers() {
  return [{
    source: '/(.*)',
    headers: [
      { key: 'X-Frame-Options', value: 'DENY' },
      { key: 'X-Content-Type-Options', value: 'nosniff' },
      { key: 'Referrer-Policy',
        value: 'strict-origin-when-cross-origin' },
      { key: 'Permissions-Policy',
        value: 'camera=(), microphone=(), geolocation=()' },
      { key: 'Strict-Transport-Security',
        value: 'max-age=63072000; includeSubDomains' },
      { key: 'Content-Security-Policy',
        value: "default-src 'self'; img-src 'self' data: https://res.cloudinary.com https://images.unsplash.com *.supabase.co; script-src 'self' 'unsafe-inline' 'unsafe-eval' https://sdk.mercadopago.com; connect-src 'self' https://*.supabase.co https://api.resend.com;" },
    ]
  }]
}
ALTO A-04 Cloudinary upload preset expuesto sin restricción de dominio
📁 Variable NEXT_PUBLIC_CLOUDINARY_UPLOAD_PRESET (env) · components/CloudinaryUpload.tsx
Descripción e Impacto
El upload preset de Cloudinary está expuesto en el cliente (NEXT_PUBLIC_). Si en el dashboard de Cloudinary el preset está en modo "unsigned" sin restricción de dominio, cualquier persona puede subir archivos ilimitados a la cuenta de Natuaroma desde cualquier origen.

Impacto: Costos inesperados en Cloudinary, almacenamiento lleno, posible contenido inapropiado subido.
Solución Recomendada

2. Editar el preset de Natuaroma
3. Activar "Restrict to origins": https://www.natuaroma.shop
4. Limitar tipos de archivo: solo image/*
5. Opcional: mover a signed uploads server-side para control total
ALTO A-05 Webhook HMAC desactivado en producción
📁 api/webhooks/mercadopago/route.ts línea 16
Descripción e Impacto
La función de verificación HMAC retorna true si MERCADOPAGO_WEBHOOK_SECRET no está configurado:
if (!MP_WEBHOOK_SECRET) return true

Esto significa que cualquiera puede hacer un POST al webhook simulando un pago aprobado y el sistema creará órdenes, enviará emails y generará códigos Wellness sin verificación.

Impacto: Fraude de pagos — obtener productos y acceso Wellness sin pagar.
Solución Recomendada
Inmediato — dos pasos:

1. Configurar MERCADOPAGO_WEBHOOK_SECRET en Vercel:
   Panel MP → Tus integraciones → Webhooks → Copiar secret
   Vercel → Settings → Environment Variables

2. Cambiar el comportamiento por defecto a false si no está configurado:
function verifyMercadoPagoSignature(...): boolean {
  // Si no hay secret configurado, RECHAZAR (no aceptar)
  if (!MP_WEBHOOK_SECRET) {
    console.error('[webhook] MERCADOPAGO_WEBHOOK_SECRET no configurado')
    return false  // ← cambiar de 'return true' a 'return false'
  }
  // ... resto de la verificación HMAC
}
🟡 MEDIO — Planificar para Próxima Iteración
MEDIO M-01 Sin validación de esquema (Zod)
📁 Todas las server actions que reciben FormData
Descripción e Impacto
Los inputs se leen como strings crudos sin validar su tipo, longitud o formato. Ejemplos: email no verificado como email válido, cédula puede ser texto arbitrario, contenido wellness acepta cualquier URL de YouTube, body de contenido sin límite de longitud.

Impacto: Datos inválidos en DB, errores en runtime, potencial de inyección de contenido en emails HTML.
Solución Recomendada
// npm install zod
import { z } from 'zod'

const checkoutSchema = z.object({
  email: z.string().email().max(255),
  nombre_completo: z.string().min(3).max(100),
  cedula: z.string().regex(/^[0-9]{6,12}$/),
  telefono: z.string().regex(/^[+0-9\s-]{7,20}$/),
  ciudad: z.string().min(2).max(100),
  direccion: z.string().min(5).max(300),
})

const result = checkoutSchema.safeParse(rawData)
if (!result.success) {
  redirect('/checkout?error=Datos de envío inválidos')
}
const data = result.data // tipado y validado
MEDIO M-02 JSON.parse sin try-catch en checkout
📁 checkout/actions.ts línea 24
Descripción e Impacto
const cartItems = JSON.parse(cartItemsRaw) — si cartItemsRaw llega corrupto, la action lanza una excepción no manejada (error 500). El webhook SÍ tiene try-catch pero el checkout NO.
Solución Recomendada
let cartItems: CartItem[]
try {
  const parsed = JSON.parse(cartItemsRaw)
  if (!Array.isArray(parsed) || parsed.length === 0) {
    throw new Error('invalid cart')
  }
  cartItems = parsed
} catch {
  redirect('/checkout?error=Carrito inválido, recarga la página')
}
MEDIO M-03 Sin timeout en fetch a Telegram
📁 registro/actions.ts línea 11
Descripción e Impacto
El fetch a la API de Telegram no tiene timeout. Si el bot está caído, la server action del registro físico queda colgada hasta que Vercel aplique su timeout global (~30s), bloqueando completamente la respuesta al usuario que acaba de escanear el QR.
Solución Recomendada
await fetch(telegramUrl, {
  method: 'POST',
  signal: AbortSignal.timeout(5000), // 5s máximo
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(payload),
})
MEDIO M-04 Sin transacciones DB en operaciones críticas
📁 checkout/actions.ts · api/webhooks/mercadopago/route.ts
Descripción e Impacto
El flujo insert orden → insert order_items → insert wellness_access → actualizar early_access_sent se ejecuta en queries separados. Si uno falla a mitad, los datos quedan inconsistentes: orden sin items, pago aprobado sin código Wellness, etc. No hay rollback automático.
Solución Recomendada
-- En Supabase SQL Editor, crear función transaccional:
CREATE OR REPLACE FUNCTION process_payment(
  p_order_id uuid, p_payment_id text,
  p_wellness_code text, p_email text
) RETURNS void LANGUAGE plpgsql AS $$
BEGIN
  UPDATE orders SET payment_status = 'paid'
    WHERE id = p_order_id;
  INSERT INTO wellness_access(code, user_email, source, status)
    VALUES (p_wellness_code, p_email, 'purchase', 'active');
  -- Todo o nada — si falla algo, rollback automático
END;
$$;
MEDIO M-05 Sin índice en user_email ni user_id en tablas críticas
📁 Tabla wellness_access · Tabla user_habits en Supabase
Descripción e Impacto
El campo user_email se consulta constantemente con .eq("user_email", email) para verificar duplicados. Sin índice, estas queries escalan linealmente con el volumen de registros. Con 10,000+ usuarios, el checkout y el registro físico se volverán lentos.
Solución Recomendada
-- En Supabase SQL Editor:
CREATE UNIQUE INDEX idx_wellness_email
  ON wellness_access (user_email);

CREATE INDEX idx_habits_user
  ON user_habits (user_id, habit_name);

CREATE INDEX idx_orders_email
  ON orders (customer_email);

-- El índice UNIQUE también garantiza unicidad a nivel DB,
-- no solo en el código de la aplicación.

BAJO B-04 Logs verbose con PII en producción
📁 lib/email.ts · checkout/actions.ts · registro/actions.ts
Descripción e Impacto
Múltiples console.log() exponen emails, nombres y números de orden en los logs de Vercel. Cualquier acceso a los logs expone PII (Información Personal Identificable) de clientes.

Impacto: Privacy / posible incumplimiento de GDPR o Ley 1581 (Colombia).
Solución Recomendada
// lib/logger.ts
const isDev = process.env.NODE_ENV === 'development'

export function log(msg: string, ...args: unknown[]) {
  if (isDev) console.log(`[INFO] ${msg}`, ...args)
}
export function logError(msg: string, err?: unknown) {
  // En prod: loggear el mensaje pero no el detalle con PII
  console.error(`[ERROR] ${msg}`, isDev ? err : '')
}

4.3 ¿Cuándo agregar Colas?

Para el volumen actual no son necesarias. Las colas agregan complejidad operacional. El umbral para considerarlas es:

  • Más de 50 órdenes/día — donde un pico puntual podría saturar Resend o Supabase
  • Cuando se agreguen más pasos al flujo post-pago (SMS, notificaciones push, actualización de CRM)
